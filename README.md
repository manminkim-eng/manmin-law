## 2. 매월 갱신 절차

### 한 줄 요약 — `publish.py`

```bash
python publish.py collect          # ① 수집 (직전 달)
#   ② 초안에서 실을 항목을 고르고 summary·reason·impact 를 채운다  ← 사람이 하는 부분
python publish.py check            # ③ 발행 전 점검
python publish.py release --push   # ④ 점검 → 빌드 → 커밋 → 푸시
```

`check` 는 README 의 발행 규칙을 실행 가능한 형태로 옮긴 것이다. `reason` 이 빈 항목,
수집 실패가 기록된 단계, `published` 날짜 규칙 위반 등이 있으면 **발행을 막는다.**
2026-08호에서 "6단계 완주" 과장과 추정 `reason` 이 그대로 나간 일이 있었고,
그런 상태를 사람이 기억으로 걸러내는 데 의존하지 않기 위한 장치다.

아래 ①~④는 각 단계의 상세 설명이다.

### 발행 시점 — 첫째 화요일에 **직전 달** 호를 낸다 (2026-08 확정)

| 발행일 | 만드는 호 | 담기는 기간 |
|---|---|---|
| 2026-09-01(화) | 2026년 8월호 | 8/1 ~ 8/31 |
| 2026-10-06(화) | 2026년 9월호 | 9/1 ~ 9/30 |
| 2026-11-03(화) | 2026년 10월호 | 10/1 ~ 10/31 |

당월 호를 당월 초에 내면 그 달 자료가 며칠치밖에 없다. 실제로 08호는 8/4 발행이라
8월 3일치만 담겨 9건이었고, 7월 한 달이 담긴 07호는 24건이었다. 호별 건수 차이가
개정량이 아니라 **발행 시점 때문에** 생긴 것이다. §2-1 이 수집 출처를 통일한 것과
같은 이유로 발행 시점도 고정한다.

`published` 는 실제 발행일(첫째 화요일), `label` 은 자료가 담긴 달이다.
2026-09-01 에 내는 호는 `issue: "2026-08"` · `label: "2026년 8월"` · `published: "2026-09-01"`.

> **전환 안내** — 08호는 이 규칙을 정하기 전인 2026-08-04 에 8월 3일치만 담아
> 잠정 발행했다. 2026-09-01 에 8월 한 달을 마저 채워 완성본으로 갱신하고
> `published` 를 `2026-09-01` 로 고친다. 05~07호는 이미 발행된 그대로 둔다.

### ① 수집 — 예고·발의 단계

```bash

python collect.py --month 2026-09  # 특정 월을 다시 만들 때만
```

입법예고 · 행정예고 · 의원발의 · 국회통과를 자동 수집해
`data/_inbox/YYYY-MM_수집.json` 초안을 만듭니다. 자세한 내용은 **2-1. 통일 수집 기준** 참고.

### ② 데이터 파일 작성

`data/` 폴더에 `YYYY-MM.json` 을 만들고, 수집 초안에서 고른 항목에
`summary` · `reason` · `impact` 를 채워 넣습니다.
여기에 **LawMCP 로 조사한 공포·시행 확정분**(`시행법령` · `훈령예규고시`)을 더합니다.

```bash

```

## 2-1. 통일 수집 기준 (2026-08 확정)

### 왜 만들었나

호별 건수가 크게 달랐다. 실제 개정량 차이가 아니라 **수집 출처가 달라서** 생긴 왜곡이다.

| 수집 출처 | 해당 호 | 평균 건수 |
|---|---|---|
| 협회 법규교육 PPT | 2025-09·10·12, 2026-01·07 | 11.2건 |
| LawMCP(국가법령정보센터) 조사 | 2026-05·06·08 | 4.3건 |

LawMCP 는 **공포·시행이 확정된 것**만 다룬다. 입법예고·행정예고·의원발의는
국민참여입법센터·의안정보시스템 소관이라 LawMCP 범위 밖이다.
2026-07호 18건 중 12건(67%)이 이 미확정 단계 항목이었다.
PPT 는 비정기 발간이라 매월 기준으로 삼을 수 없다.

### 매월 반드시 훑을 4개 단계

| 단계 | cat | 출처 | 도구 |
|---|---|---|---|
| 공포·시행 확정 | `시행법령` | 국가법령정보센터 | LawMCP |
| 고시·훈령·예규 | `훈령예규고시` | 국가법령정보센터(행정규칙) | LawMCP |
| 입법예고 | `입법예고` | 국민참여입법센터 | `collect.py` |
| 행정예고 | `행정예고` | 국민참여입법센터 | `collect.py` |
| 의원발의 | `의원발의` | 의안정보시스템 | `collect.py` |
| 본회의 통과 | `국회통과` | 의안정보시스템 | `collect.py` |

**어느 한 단계라도 빠지면 그 호는 발행하지 않는다.** 해당 단계에 실적이 없으면
0건임을 확인한 것이므로 그대로 두고, "자료를 못 구해서 뺀 것"과 구분한다.

> 2026-08-05 국민참여입법센터 OC 가 승인되어 **4단계 모두 수집 가능해졌다.**
> 인증 대기 중 임시로 두었던 예외 조항은 이때 삭제했다. 05~07호는 예고 2단계가
> 빠진 채 발행된 호들이다.

### 법령 화이트리스트는 `data/domain_filter.json` 에 있다 (2026-09 분리)

`collect.py` 는 수집한 제목이 실무 분야에 걸리는지를 법령명 화이트리스트로 판정한다.
예전에는 그 목록이 `collect.py` 안에 파이썬 리스트로 박혀 있었다. 두 가지가 문제였다.

- 법령 하나 추가하려고 스크립트를 고쳐야 했다
- **죽은 항목을 아무도 몰랐다.** 「신에너지 및 재생에너지 개발·이용·보급 촉진법」을
  `신재생에너지` 로 적어 둔 항목이 한 번도 매칭되지 않았고, 2026-09 에 협회 PPT 와
  대조하고 나서야 드러났다. 그 사이 8월 시행령 개정(건축물 공급의무비율을
  재생에너지만으로)을 놓쳤다

이제 목록은 데이터 파일이라 **깃허브 웹에서 바로 고칠 수 있다.** 그리고 `collect.py` 가
매 실행마다 항목별 매칭 횟수를 `data/domain_filter_stats.json` 에 누적하고,
한 번도 걸리지 않은 항목을 실행 끝에 알린다. `publish.py check` 도 같은 값을 본다.

한 달 0회는 그 달에 개정이 없었을 뿐일 수 있다. **여러 달 연속 0회면 제명이 틀렸거나
폐지된 것이니 `match` 값을 확인한다.** 실제로 이 장치를 넣자마자 `건축물의 설비기준`
항목이 중복 등록돼 있는 것이 드러났다.

#### 의도적으로 제외한 법령

`domain_filter.json` 의 `excluded` 에 적어 둔다. **넓히는 것만이 개선이 아니다** —
범위를 벗어난 법령이 섞이면 호가 산만해지고 독자가 걸러 읽어야 한다.

| 법령 | 결정 | 사유 |
|---|---|---|
| 농지법 | 2026-09-01 | 농지 내 편의시설·농지전용은 건축 설계·감리 실무의 대상이 아니다 |

다시 넣기 전에 `excluded` 의 결정 사유를 먼저 확인한다.

### 시행법령도 전수 스캔이 불가능하다 — 감시목록으로 대체 (2026-09)

LawMCP 에는 "이번 달에 공포된 법령 전체"를 뽑는 기능이 없다. 훈령예규고시와 같은
한계다. 그래서 `data/law_watchlist.json` 에 실무 관련 법률을 tier A(매월 필수 15건)·
tier B(여유 시 18건)로 나눠 두고, 매월 각 법률명을 `search_law` 로 조회한다.

**법률명 하나로 조회하면 시행령·시행규칙까지 부분매칭으로 함께 나온다.** 그래서
법률당 한 번이면 3종 세트를 다 본다. `search_law` 는 시행예정 개정도 자동 병기한다.

목록은 2025-09 ~ 2026-08 발행 8개 호에 **실제로 등장한 법령 빈도**로 뽑았다.
주차장법·건축법이 8개 호 중 5회로 가장 자주 바뀌었고, 소방시설법은 전 단계 통틀어
가장 많이 나왔다. 새 법령이 실무에 걸리면 목록에 추가한다.

### 훈령예규고시는 전수 스캔이 불가능하다 (2026-09 확인)

LawMCP 에는 **행정규칙을 공포일 기준으로 나열하는 기능이 없다.** `search_admin_rule` 은
명칭 검색이고 결과가 20건에서 잘리며, `advanced_search` 의 `efYd` 필터도 동작하지 않는다.
그래서 "이번 달에 공포된 행정규칙 전부"를 뽑아낼 방법이 현재로선 없다.

대신 **명칭 감시목록** 방식을 쓴다. 실무에 걸리는 행정규칙을 `data/admin_watchlist.json`
에 고정해 두고, 매월 각 명칭의 공포일을 LawMCP 로 조회해 대상 월 공포분만 골라낸다.
새 고시가 실무에 등장하면 감시목록에 추가한다.

**이 단계는 전수가 아니므로, 그 호 `source` 에 "명칭 기반 N건 점검"임을 반드시 밝힌다.**
"0건 확인"이라고 쓰면 안 된다 — 감시목록 밖에서 공포된 고시는 보이지 않기 때문이다.

### 법제처 접속 대기열 (2026-09 확인)

국민참여입법센터 API 는 접속량이 많으면 XML 대신 `Waitingroom` 대기열 HTML(약 4.4KB)을
돌려준다. User-Agent 나 `pageSize` 로는 회피되지 않는다. `collect.py` 는 브라우저처럼
**쿠키 세션을 물고 재시도**하며, 첫 페이지만 통과하면 이후 페이지는 바로 통과한다
(실측: 1페이지 13회 → 2·3페이지 각 1회).

끝내 통과하지 못하면 `collect.py` 는 그 단계를 **0건이 아니라 실패로 보고**하고
`data/_inbox/*.json` 의 `failed` 에 기록한다. 이 상태로는 발행하지 않는다.

### API 인증키 설정

수집처가 **두 곳**이고, 각각 별도 가입·신청이 필요합니다. 공공데이터포털은
이 세 건을 모두 `LINK` 유형으로만 중계하므로 **포털에서는 키가 발급되지 않습니다.**

| 항목 | 값 |
|---|---|
| 엔드포인트 | `https://open.assembly.go.kr/portal/openapi/nzmimeepazxkubdpn` |
| 인증 | `KEY` (쿼리 파라미터) |
| 필수 | `AGE=22` (22대 국회), `Type=json`, `pIndex`, `pSize` |
| 정렬 | 발의일(`PROPOSE_DT`) 내림차순 |

#### ② 국민참여입법센터 — 입법예고 · 행정예고  *(2026-08-05 승인 완료)*

`도움말 > 서비스 안내 및 정보공개 > 정보공개활용 > [정보공개 신청정보]` 에서 신청합니다.
(비회원·간편가입 상태에서는 신청 화면이 열리지 않습니다.)

| 항목 | 값 |
|---|---|
| 입법예고 목록 | `https://www.lawmaking.go.kr/rest/ogLmPp.xml` |
| 행정예고 목록 | `https://www.lawmaking.go.kr/rest/ptcpAdmPp.xml` |
| 인증 | `OC` = 신청 계정 ID 의 **@ 앞부분** |
| 기간 | `stYdFmt` · `edYdFmt` = `YYYY. M. D.` (공백 포함) |
| 페이징 | `pageIndex` · `pageSize` — **기본값이 20 이라 안 주면 한 달치가 잘린다** (100 확인됨) |
| 응답 | **XML 전용** — JSON 미지원 |
| 날짜 필드 | `pntcDt` · `stYd` · `edYd` 모두 `2026. 7. 31.` 형식 (월·일 한 자리) |
| 제목 | `[진행]`·`[완료]` 상태 접두어가 붙어 나온다 — 떼고 써야 법령명이 잡힌다 |
| 원문 | `ogLmPpSeq` → `opinion.lawmaking.go.kr/gcom/ogLmPp/{seq}` (행정예고는 `/gcom/admpp/{seq}`) |
| 미승인 시 | `<result><retMsg>401</retMsg></result>` |

입법예고 출력 필드는 `lsNm`(예고명) · `lsClsNm`(법령종류) · `asndOfiNm`(소관부처) ·
`pntcNo`(공고번호) · `pntcDt`(공고일) · `stYd`~`edYd`(예고기간) 입니다.
행정예고는 예고명이 `admRulNm` 으로 바뀝니다.

#### ③ 설정 파일

`config.example.json` 을 복사해 `config.local.json` 을 만들고 값을 채웁니다.

{
  "assembly": { "key": "열린국회정보 인증키", "age": "22" },
  "moleg":    { "oc": "국민참여입법센터 정보공개 신청 계정 ID 의 @ 앞부분" }

`config.local.json` 은 `.gitignore` 에 등록되어 있습니다. **저장소에 올리지 마십시오.**
`oc` 가 비어 있으면 예고 2종은 건너뛰고 의안 수집만 수행합니다.

### 매월 실행 절차

```bash
cd "41.개발자료[건축법규]\버전s-1.0"

python collect.py --probe          # 최초 1회 — 인증·응답 형태 확인
python collect.py                  # 직전 달 수집 → data/_inbox/YYYY-MM_수집.json
```

수집 결과는 **초안**이다. 그대로 발행하지 않는다.

1. 초안에서 실무 영향 있는 항목만 고른다
2. `summary` · `reason` · `impact` 를 채워 `data/2026-09.json` 의 `items` 에 붙인다
3. LawMCP 로 공포·시행 확정분(`시행법령` · `훈령예규고시`)을 조사해 추가한다
4. `python build.py`

`collect.py` 는 제목 키워드로 건축·구조·기계설비·소방·토목·전기 분야만 걸러내고,
`data/` 의 기존 호와 중복되는 항목은 자동으로 제외한다.
필터 키워드는 `collect.py` 상단 `DOMAIN` 딕셔너리에서 조정한다.

## 3. JSON 작성 규칙

```jsonc
{
  "issue":    "2026-08",                    // 파일명과 동일 (필수)
  "label":    "2026년 8월",                 // 화면 표시명
  "published":"2026-09-01",                 // 발행일
  "source":   "법규교육 PPT(26년08월).pdf",  // 원본 자료명
  "headline": "이번 호 핵심 3줄 요약",

  "items": [
    {
      "cat":  "시행법령",
      "field":["건축","소방"],
      "law":  "건축법 시행령",
      "title":"항목 제목",
      "dateLabel":"시행",
      "date": "2026-08-15",
      "deadline": "2026-09-20",             // (선택) 예고 마감일 → D-day 자동표시
      "summary":"한두 문장 요약",
      "reason": "제안이유 및 주요내용 (개정 배경·취지 서술)",
      "detail":[ "조문별 세부내용", "..." ], // (선택) 접었다 펴는 영역
      "compare":[ {"a":"제61조①","o":"현행 조문 요지","n":"개정(안) 요지"} ], // (선택) 신·구조문 대비표
      "compareNote":"대비표가 없을 때 사유(제정법·시행예정본 미공개 등)",   // compare 없을 때만
      "impact":"실무 영향 한 줄",            // (선택) 금색 강조 박스
      "billId":"PRC_...",                   // (선택) 의안 고유번호 — 중복 재수집 방지
      "link":"https://...",                 // (선택) 원문 링크 직접 지정
      "linkLabel":"제정안 원문 ↗"           // (선택)
    }
  ]
}
```

### cat (구분) — 이 7가지만 사용

| 값 | 색상 | 용도 |
|---|---|---|
| `시행법령` | 금색 | 이미 공포·시행 확정 |
| `국회통과` | 적색 | 본회의 통과, 공포 대기 |
| `훈령예규고시` | 보라 | 고시·훈령·예규 |
| `입법예고` | 청색 | 법령 입법예고 |
| `행정예고` | 녹색 | 지침·시방서 행정예고 |
| `의원발의` | 주황 | 발의 단계 |
| `추가검토` | 회색 | 지자체 운영기준·KDS·참고자료 |

### reason 은 원문 전재가 원칙 (2026-09 확정)

`reason`(제안이유 및 주요내용)은 **공고·법령 원문을 그대로 옮긴다.** 제목만 보고
내용을 추론해 쓰지 않는다.

2026-08호 발행 당시 예고 10건의 `reason` 을 예고안 본문을 열지 않고 제목에서
추론해 썼는데, 나중에 원문을 대조하니 **5건이 실제 내용과 달랐다.** 예를 들어
「다중생활시설 건축기준」은 "실별 최소면적·복도 유효너비" 개정으로 적혀 있었으나
실제는 고시원의 학습시설 구비·욕조 설치 금지 완화였다.

- 예고 항목의 원문은 `link` 의 공고 상세 페이지에 **서버 렌더링으로 그대로 들어 있다.**
  `1. 개정이유`(또는 `제안이유`) 부터 `N. 의견 제출` 직전까지가 본문이다.
  부처마다 목차 번호가 다르므로 그 점만 감안하면 기계적으로 추출된다.
- 원문을 끝내 확인하지 못했으면 추정으로 채우지 말고, 그 사실을 항목에 밝힌다.
- 법규 요약본이라 실무자가 그대로 믿는다. 추정 서술은 오독을 만든다.

### billId (의안 고유번호) — 의원발의·국회통과 항목에 권장

발행할 때 의안명을 실무 표현으로 바꿔 씁니다. 예를 들어 08호의
「공장·창고 화재위험등급 평가 및 보수·보강 조치 의무」는 실제 의안명이
「건축물관리법 일부개정법률안」입니다. 제목이 달라지면 `collect.py` 의 제목 기반
중복 판정이 새서 **다음 달 초안에 같은 의안이 다시 올라옵니다.**

수집 초안(`data/_inbox/*.json`)의 `_billId` 값을 `billId` 로 옮겨 적으면 제목을
아무리 바꿔도 확실히 걸러집니다. 화면에는 표시되지 않는 관리용 필드입니다.

### field (분야)

`건축` `구조` `기계설비` `소방` `토목` `전기` `도시계획` `안전진단` `환경` 등 자유롭게.
필터 칩이 자동 생성됩니다.

### 원문 링크 자동 생성 규칙

| 자료 유형 | 연결되는 곳 |
|---|---|
| 일반 법령·시행령·시행규칙 | 법제처 `law.go.kr/법령/OOO` |
| 고시·훈령·예규 (`ADMIN_RULES` 등록분) | 법제처 `law.go.kr/행정규칙/OOO` |
| KDS·KCS·표준시방서 | 국가건설기준센터 `kcsc.re.kr` |
| 조례 | 자치법규정보시스템 `elis.go.kr` |
| 조달청 기준 | 나라장터 `pps.go.kr` |
| 의원발의·국회통과 | 2차 링크가 의안정보시스템으로 연결 |
| 입법·행정예고 | 2차 링크가 국민참여입법센터로 연결 |

새 고시가 추가되면 `build.py` 의 `ADMIN_RULES` 집합에 법령명을 넣어주면 됩니다.
어느 규칙에도 안 맞으면 JSON에 `"link"` 를 직접 써서 지정하세요.

## 4. 사이트 기능

| 기능 | 설명 |
|---|---|
| 검색 | 법령명·조문·키워드 실시간 필터. 단축키 `/` |

| 공유 | 모바일은 카카오톡 등 네이티브 공유, PC는 링크 복사 |

예를 들어 `소방` 분야만 필터한 뒤 추출하면 소방 관련 원고만 나옵니다.
